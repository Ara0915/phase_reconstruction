# 給接手對話的說明：如何向 Elvis 解釋執行步驟

> 這份文件說明 Elvis 偏好的步驟說明方式。
> 他在 NCHC Nano 5 上跑深度學習相位回復專題，需要照步驟操作 HPC。
> 請在給他任何「執行步驟」時遵守以下格式與內容要求。

---

## 一、先講「這個實驗在做什麼」

**在給指令之前，用一兩句話說明這個實驗要回答什麼問題、結果怎麼判讀。**

不要一開始就丟指令。他需要先知道「為什麼要做」才能判斷過程中哪裡不對。

範例：

> 這個實驗就是日誌 §13.5 記的那個：把條件拉到接近理論理想（沒有 beamstop、
> 高劑量、高過取樣），看相位未知的正常路徑能不能大幅變好。它在檢驗老師說的
> 「二維理論上有唯一解」。

---

## 二、每一步的固定格式

```
## ①  步驟標題（標明在哪裡執行：本機 / 登入節點 / 計算節點）

（指令區塊）

一句話說明為什麼要這樣做，或要確認什麼。
⚠️ 若有陷阱，明確標出。
```

**規則：**

- **用圓圈數字 ① ② ③** 分步，每步一個 `##` 標題
- **每步標題寫清楚在哪台機器執行**（本機 PowerShell / 登入節點 / 計算節點）
- **指令放在 code block**，可直接複製
- **指令下方一到兩句說明「為什麼」**，不要只丟指令
- **檢查項目用表格**，欄位為「檢查 | 為什麼」
- **有陷阱就用 ⚠️ 標出**，並說明後果（例如「不加會連不上」「sbatch 會直接失敗」）
- **不要把多個概念塞進同一段文字**，一步只做一件事

## 三、HPC 的硬性規則（不可違反）

### 3.1 所有 python 一律在計算節點執行

**Elvis 曾因在登入節點執行 python 而被 NCHC 列入黑名單、帳號被鎖，
並需寫信向管理員道歉。** 這是非常不愉快的經驗。

- 任何 `python ...` 指令（無論多小、多快）都必須在計算節點
- 登入節點**只能**做：`sbatch`、`squeue`、`ls`、`cat` 這類查詢與送件
- 給指令前，先帶他進計算節點，並提醒「提示字元變成 `hgpn` 開頭才往下」
- **不要**用「這只要幾秒鐘」當理由叫他在登入節點跑 python

進計算節點的標準指令：

```bash
srun -A mst114378 -p dev --gres=gpu:1 -c 8 -t 01:00:00 --pty bash
```

### 3.2 兩個已知的坑（其他對話曾經寫錯）

**坑一：scp 必須加 `-P 2222`**

```powershell
scp -P 2222 檔案 elviss0915@nano5.nchc.org.tw:/home/elviss0915/
```

- 傳檔走 2222 埠，**大寫 `-P`**
- SSH 登入則**不加**埠號（2222 是 sftp-only，拿來登入會被拒）
- 若出現 `protocol error: mtime.sec not present`，加 `-O`

**坑二：conda 環境不可用 `$(conda info --base)`**

❌ 錯誤寫法（`module load` 之後 conda 還不在 PATH，會報 `conda: command not found`）：

```bash
source "$(conda info --base)/etc/profile.d/conda.sh"
```

✅ 正確寫法（用絕對路徑）：

```bash
module purge && module load miniconda3/24.11.1 cuda/12.4
source /work/HPC_software/LMOD/miniconda3/miniconda3_app/24.11.1/etc/profile.d/conda.sh
conda activate /work/elviss0915/envs/cdi
```

**若新寫的 `.sh` 腳本裡有 `conda info --base`，一定要提醒他修掉**，
否則 sbatch 送出後 job 會直接失敗：

```bash
grep -n "conda info" *.sh
sed -i 's|source "$(conda info --base)/etc/profile.d/conda.sh"|source /work/HPC_software/LMOD/miniconda3/miniconda3_app/24.11.1/etc/profile.d/conda.sh|' 檔名.sh
```

### 3.3 其他環境事實

| 項目 | 值 |
|---|---|
| 帳號 / 計畫 | `elviss0915` / `mst114378` |
| 登入節點 | `cbi-lgn01` |
| 計算節點提示字元 | `hgpn` 開頭 |
| 程式目錄 | `/home/elviss0915/cdi` |
| 結果目錄 | `/work/elviss0915/runs` |
| 併發上限 | 同時最多 2 個 job（`QOSMaxJobsPerUserLimit`） |
| **訓練用 partition** | **`normal2`（H200）—— 所有 `run_*.sh` 一律使用** |
| 互動 session | `dev`（2 小時上限，只拿來進計算節點做檢查與分析） |
| 其他 | `normal`（H100）通常排隊較嚴重（曾有 40 個 job 在排），不使用 |

### 3.4 新腳本的 partition 要改成 normal2

其他對話產生的 `.sh` 腳本可能預設 `-p normal`。**送件前一定要檢查並改成 `normal2`**：

```bash
grep -n "SBATCH -p" run_xxx.sh
sed -i 's/^#SBATCH -p normal$/#SBATCH -p normal2/' run_xxx.sh
```

不要寫成「排太久再改」—— 直接在送件步驟前改掉。

### 3.5 更新檔案時不要整包覆蓋

Elvis 在國網上改過部分檔案（`.sh` 的 partition、conda 路徑）。
**先解壓到旁邊的資料夾，再只複製新檔案**：

```bash
unzip -q cdi_slurm.zip -d ~/cdi_new
cp ~/cdi_new/cdi/新檔案 ~/cdi/
```

## 六、解釋概念的方式

- **Elvis 偏好詳細解釋，不要為了省篇幅而縮減。** 他明確表示過詳細說明對他很重要
- **預設先給完整版**（步驟與結果解釋都一樣）：完整的背景、判讀與陷阱都寫出來。他聽不懂或嫌太複雜時會主動說「講簡單點」，那時再給精簡版（2026-09-26 他明確這樣要求）
- 精簡版的寫法：只留必要指令（每步一兩行說明）、進度用一行 `ls … | wc -l` 看數字、結果用「一句話 + 小表格」
- **他說「太難了」時，換一種方式重講**（比喻、具體數字、拆步驟），不要重複同一套說法
- **用具體數字舉例**，例如「劑量拉高 100 倍 → log 多 ln(100) ≈ 4.6」
- **他的追問常常抓到錯誤**，認真對待每個「為什麼」
- **自己講錯時直接說明並撤回**，不要迴避
- 若另一個對話寫的檔案你看不到內容，**直接說明無法檢查**，不要假裝已驗證

## 六之二、文件更新規則

- **研究日誌只在 Elvis 明確說「更新研究日誌」時才更新**，一次把該段落的進度寫完（他要確認研究到一個段落，才有跟著進度走的感覺）。平常的結果只記在實驗協定、優化方案等工作文件。
- **每次更新研究日誌都要升版本號**（v11 → v12 …）：標題的「版本」行寫新版本與日期、摘要加該版的「須註明」區塊、各章標題註明版本；另存一份 `研究日誌_CDI相位回復_vNN.md`，**並用檔案傳送（SendUserFile）直接給 Elvis 下載**（Project 裡的文件沒有明顯的下載按鈕，他習慣從檔案卡片下載帶版本號的檔）；Project 裡的 `claude/研究日誌_CDI相位回復.md` 同步更新。
- 實驗協定、優化方案等工作文件可隨結果更新（寫定 → 結果 → 修正），修正一律以「須註明」或「修訂」標示，不刪原文。
